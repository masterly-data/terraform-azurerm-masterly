### Changed

- **Zone-redundant Postgres HA is off by default on every capacity profile, and `mode = "production"` no longer requires it (ADR 0120, 2026-11-20 amendment).** `postgres_zone_redundant_ha` now defaults to `false` instead of `null`, and no `capacity_profile` turns it on: `standard` and `enterprise` size the SKU, the pooler and the replica floors only. By default the install's Container Apps environments are not zone-redundant, so the standby protects the data more than it protects uptime, at twice the server's compute. Without it, a zone failure is recovered by a point-in-time restore (Azure documents up to 5 minutes of data loss). `mode = "production"` with `capacity_profile = "enterprise"` and HA off plans with a warning, `enterprise_production_without_postgres_ha`, because the enterprise profile's recovery objectives assume the standby. `postgres_zone_redundant_ha = true` on a burstable SKU is still refused. See `docs/scaling.md`, "Zone-redundant HA".

  **Migration.** An install that set `capacity_profile = "standard"` or `"enterprise"` and left `postgres_zone_redundant_ha` unset had a standby, and on this version plans removing it, an in-place update that restarts the server. To keep the standby, set `postgres_zone_redundant_ha = true` before you upgrade. An install that sets the input explicitly, or sets no profile, plans no change. The input is no longer nullable: an explicit `postgres_zone_redundant_ha = null` (for example passed through from a wrapper variable) now means `false`, the default, rather than the profile's value.
