### Changed

- **One workload identity per role (ADR 0120 §6): no Container App identity holds Key Vault Crypto Officer.** `ca-api` keeps its identity, `id-<prefix>-apps`, and `ca-workers` runs as `id-<prefix>-workers`, so the two never share an identity or an `AZURE_CLIENT_ID` except in the one shape below. The built-in Key Vault Crypto Officer, which could delete, purge, back up, restore and rotate every key in the vault, is replaced by two roles the module defines on the data resource group, beside `Masterly app secrets`: `Masterly signing key reader (<prefix>-<suffix>)`, `keys/read` alone (a key's properties and public half, never a signature), for `ca-api`; and `Masterly signing keys (<prefix>-<suffix>)`, exactly `keys/create/action`, `keys/read`, `keys/sign/action`, `secrets/getSecret/action` and `secrets/setSecret/action`, for `ca-workers`, which creates the erasure and audit checkpoint signing keys and signs with them. **`ca-api` must run api v0.138.0 or later**, where it holds no key client ("ca-api holds no Key Vault key client", MAS-3117; erasure key creation and signing run as a core-worker job, MAS-3578): on an earlier api image erasure fails, because that `ca-api` still creates and signs. Both roles are scoped to the vault, because Azure cannot scope a role assignment to a key that does not exist yet and Key Vault's conditions do not cover keys; the vault holds no keys besides its Environments' signing keys. Like `Masterly app secrets`, creating them needs `Microsoft.Authorization/roleDefinitions/write` (Owner or User Access Administrator); run `scripts/preflight.sh --principal <deployer object id>` first.
- **`ca-workers` runs as its own identity on an install without the Key Vault too.** Until now an install with `enable_workers = true` and `enable_key_vault = false` (an evaluation install in `mode = "demo"`) ran `ca-workers` as `id-<prefix>-apps`. Upgrading creates `id-<prefix>-workers` there, with its grants, and moves `ca-workers` to it; `id-<prefix>-apps` gives up Service Bus Data Receiver and the jobs queue's Data Owner to it, as it already did on installs with the vault. With `acr_id` null, grant AcrPull to `workers_identity_principal_id` before applying. The one shape where `ca-workers` still runs as `id-<prefix>-apps` is `migrations = "start"` with `database_auth = "entra"` on the starter server, where both apps sign in to Postgres as that identity because both migrate; that identity then holds the signing keys role as well.
- **`migrations` defaults to `"job"` for a new install in `mode = "production"`** (MAS-5130). The migrate job, `caj-migrate`, is then the only Postgres administrator, and `ca-api` and `ca-workers` connect as the DML-only roles it creates (`masterly_api`, `masterly_workers`), so in production's default no Container App identity is a database administrator. Other modes keep `"start"`. `migrations` itself now defaults to null; an explicit value wins as before. Known gap of api v0.138.0, the default image: under `"job"`, deleting an Environment leaves its database on the server. The fix (MAS-5128) is on the backend's main branch and in no release yet; until one carries it, drop such a database yourself.

  **Migration note — an existing production install with `migrations` unset.** The module looks for the install's `ca-api` and `caj-migrate` in its apps resource group. An install whose `caj-migrate` exists keeps `"job"`, with no change. An install that runs without it (0.26.0's default, `"start"`) is **refused at plan** with a message, rather than moved: moving a running install's databases to the migrate job is a change to customer data. Add one line and plan again: `migrations = "start"` keeps what runs today (nothing changes; on `database_auth = "entra"` the api's identity stays the server's Entra administrator, a documented departure, and every plan warns through the check `production_migrations_at_start`), or `migrations = "job"` moves the install, following "The migrate job" in `docs/data-plane.md`.

### Removed

- **The apps identity's and the workers identity's Key Vault Crypto Officer grants.** `ca-workers`' new grant, `kv_signing_keys_workers`, is created before `ca-workers`' update, and `kv_crypto_officer_workers` is removed after it, because `ca-workers` recorded a dependency on it. `ca-api`'s grant is replaced at its own address (a `moved` block from `kv_crypto_officer` to `kv_signing_key_reader`), destroy then create, as `Masterly app secrets` replaced Secrets Officer: for the seconds between the two, and until Azure propagates the new grant, `GET /v1/audit/signing-key`, the audit export and online verify can fail on `ca-api`, and succeed when retried. Nothing else `ca-api` does reads a key. Nothing replaces the Postgres server, the vault, the Service Bus namespace or an environment. `ca-api` keeps ACS Email Owner: api v0.138.0 sends organization invitations and notification verification codes from the request, in `ca-api`, so the grant cannot move to `ca-workers` alone yet.
